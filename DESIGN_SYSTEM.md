# Design
Fast, friendly, trustworthy map utility. Playful, not childish.
Primary blue #1E90FF; teal #00B3A6; light neutral surfaces. Accessible semantic status tokens.
Rounded cards/buttons, large targets, strong hierarchy, high contrast, minimal urgent-use steps.
Plain/Risqué changes copy/rating visuals, not information architecture/accessibility.
Home must answer quickly: where am I; nearest usable restroom; distance/time; can I use it; navigate.
Location detail prioritizes name/address, distance/ETA, rating, verification, key/purchase/accessibility, amenities/issues, Navigate, Report/Correct, Favorite.
No user-uploaded photos.

## R1 shared foundation (consumer redesign milestone, 2026-10-09)
Direction: calm, high-contrast utility. One column on phones, list + map side by side from 900 px. Answer first (nearest usable restroom, distance, walk time, can I use it), explain second. Every state (asking, locating, denied, loading, offline, error, empty, filtered-empty) is a plain-language banner with exactly one next step. Discovery never asks for an account.

Tokens (`packages/ui/src/tokens.ts`, contrast enforced in `tokens.test.ts`): `colors`, `spacing`, `radii`, `typography`, `touchTarget` (48 dp minimum, 56 primary), plus new `breakpoints`/`layout`/`layoutFor` (responsive), `focusRing` (3 dp outline in strong blue, offset 2; >= 3:1 against all surfaces) and `tones` (info/success/warning/danger text+background pairs, each with a symbol so tone is never color alone). Brand blue #1E90FF is for fills and large graphics only; text and white-on-color use the Strong variants.

Components (`apps/mobile/src/components`): `Screen` (safe areas, max width 1120, h1 title + subtitle), `StatusBanner` (tone, title, message, actions; `urgent` = alert, otherwise polite status), `SegmentedControl` (one radio group, e.g. List | Map), `Chip`, `PrimaryButton`, `SecondaryButton`, result cards in `LocationList` (name heading, distance + walk time, badge, only-known facts, community rating, "Nearest" label), `FilterPanel` (disclosure + always-visible removable active-filter chips + Clear all), `focus.ts` (`useFocusStyle` visible keyboard focus, `spaceActivates` Space for radios/checkboxes).

Accessibility rules adopted: state is exposed with `aria-checked` (radios and checkboxes; never aria-selected) / `aria-expanded` (disclosure buttons; actions use role=button with no checked state) / `aria-disabled` (react-native-web does NOT translate `accessibilityState`, so Chips and toggles previously exposed no state on the web: fixed); list rows are `role=list`/`listitem` containing a link; one level-1 heading per screen; every control has an accessible name and is >= 48 px tall; no horizontal scroll at 320 px; unknown facts are never displayed as negatives; ratings are always labeled "Community rating".

Radio groups (`RadioGroup`, `SegmentedControl`): ARIA radio pattern with roving focus (`useRovingRadios`): one Tab stop, Arrow keys move selection and focus with wrap. Purchase filter copy: "No purchase needed" / "No purchase required" - never "Free", because a purchase requirement says nothing about a usage fee.

## R2 detail + reporting (2026-10-09)
Reading order on a phone: name (h1) -> status block (address, distance/travel, verification badge, community rating, quick facts of KNOWN access facts only) -> Get there -> Access -> Amenities -> About these details -> Save, rate and check in -> Something wrong?. From 900 px the facts sit in a left column and the action sections in a right column (same DOM order, so keyboard order matches reading order). Facts are a real list; each value is a symbol plus a word (`✓ Yes`, `✕ No`, `? Not reported`) so unknown never reads as no and nothing depends on color. Ratings are always "Community rating"; none yet reads "No community ratings yet". Unverified restrooms carry a warning banner and the badge. Every load/missing/invalid/error state is a StatusBanner with a next step; failures are announced as alerts; success is a polite status. Write actions (rating, favorite, check-in, report) hold a synchronous in-flight lock and keep the typed form after a failure. Signed-out visitors keep full read access; account actions show one "Sign in to continue" banner and the correction/report buttons lead to the gated screens, which carry the destination through sign-in. Report copy states that "closed or gone" means permanently closed; temporary closures go under "Something else".

## R3 accounts + contributions (2026-10-09)
Forms and account pages use `Screen form` (640 px column on wide screens) and the shared `Section` cards and `StatusBanner` notices, so every state has one place to look: errors are danger alerts, confirmations are polite success banners, "what to do next" actions sit inside the banner. `TextField` takes an `error` (marks the input `aria-invalid`, shows the message under the field). Long forms are grouped into labeled sections (About the place, Access and facilities, Location, Before you send); "Not sure" is described as unknown, not "No". Every write path (sign-in, sign-up, reset, settings, display name, new restroom, correction, report, account deletion) holds a synchronous in-flight lock, keeps typed input after any failure, and explains the specific refusal (caps, rate limits, pending correction). The success state of a contribution says it is pending review and offers a way back. Provenance copy never claims a source it cannot know: attribution appears only when present, otherwise "Details can change".

Uncertain outcomes (R3 correction): a write that fails WITHOUT a structured server error code (dropped connection, lost response, gateway error) may still have committed, so the API layer marks it `uncertain`, the UI shows a warning "Not confirmed" notice (`uncertainWriteMessage`: "We couldn’t confirm whether ...; we never resend automatically, so check first and then try again if needed"), keeps all typed input and never retries by itself. Only a coded server rejection (caps, rate limit, validation, auth) is described as "not done". A confirmed account deletion stays confirmed even if clearing the local session fails; the page then explains the device-level clean-up separately and offers "Sign out of this device".

## R4 integration (2026-10-09)
Pushed screens (restroom detail, report, contribution, sign-in, reset, callback) move focus to the page heading on open (`Screen moveFocus`; the heading takes programmatic focus only and shows no ring). Tab roots do not, so keyboard users keep their place in the tab bar. Every screen content block is a `main` landmark and the tab bar wrapper is labeled as navigation. Result cards and the verified hint are links that open with Enter. Discovery filters and the List | Map choice live for the app session (`state/discoverySession.ts`), so opening a restroom and going back keeps them. Global web rules (`web/globalStyles.ts`) give tab links and Leaflet controls a visible focus ring, make map zoom controls 44 px, and keep tab labels whole at 320 px.

Main navigation (R4 correction, `components/MainNav.tsx`): on web a labeled `navigation` landmark of four ordinary links (Tab and Enter, `aria-current="page"` on the open one, no item current on pushed screens such as a restroom). It deliberately does not use `tablist`/`tab` because that promises arrow-key behavior; native keeps real tab semantics (`role=tab`, selected state). Link focus rings come from focus state like every other control (`:focus-visible` alone is unreliable under WebDriver in WebKit/Firefox). On web `enableScreens(true)` makes inactive screens `display:none` (state kept), so keyboard focus and screen readers cannot reach controls behind the active screen. Tab labels use the label token (14 px) and stay whole at 320 px.

## D1 dashboard-first home (2026-10-11; owner-approved direction: about 70% premium, 30% playful, no emoji; the visual result still needs Jake's review)
**Home hierarchy** (phone, top to bottom): page title; the **nearest-restroom card** (deep brand-blue hero: name, large distance, walking estimate, honest Verified/Unverified badge, known facts only, a Directions button that opens a maps app with only the destination, and a Details link); **four quick actions** (Show map/Show list, Filters, Favorites, Add a restroom, each into an existing feature with its own auth rule; Map and Filters need a location, so before one is granted only Favorites and Add a restroom show); a labeled **search** over the restrooms already loaded (name, street, town; local only, no lookup, no geocoding); then the existing summary, filters, List|Map and result cards. Wide screens put the card, actions, search and list in the left column beside the sticky map. While a search or filter is active the card says "Nearest match", not "Nearest restroom". No points, badges, offers, photos or balances are shown anywhere (the plan for them is `VIP_REWARDS_PLAN.md`, design only).
**Icons** (`components/Icon.tsx`): a 16-icon set drawn from plain Views (search, pin, list, map, filter, heart, user, plus, check, close, info, alert, help, chevron, navigate, compass). No font, image, SVG package, new dependency or license; renders the same on web, iOS and Android; always decorative (hidden from assistive technology) next to visible text or inside a control that has its own accessible name. Used in the navigation bar (a tinted pill marks the open tab), quick actions, badges, banners, filter chips, fact marks (check / close / help beside Yes / No / Not reported) and result cards.
**Tokens** (`packages/ui`): `colors.hero/onHero/heroMuted/heroAccent`, `tiles` (blue, teal, amber, rose tint pairs for playful accents), `shadows` (one soft card elevation, one hero elevation, in the cross-platform array form). Every new text pair and the hero accent are covered by the AA contrast tests in `tokens.test.ts`. `tones` now carry an icon name instead of a glyph.
**Emoji and symbol inventory:** consumer app: none remain. Removed or replaced: the check, cross and question-mark glyphs in verification badges, fact marks, banner tones and the removable filter chip (now drawn icons; `factMark` returns an icon name). Remaining outside the consumer app (owner's call, not touched here): the admin review tool uses the star glyph for ratings and an arrow in two links (`apps/admin/src/app/review/*`); the copyright sign in OpenStreetMap attribution text is required legal text, not decoration.
**Shared navigation:** icon plus label per item; web renders ordinary links (unchanged landmark, `aria-current`), native keeps real tabs. The link style is passed to expo-router's `Link asChild` as one flattened object (a style array would be spread into numbered keys and crash the web build).
**Evidence:** `docs/evidence/d1/` (generated by `node scripts/visual-packet.mjs`) are Chromium screenshots in emulated viewports against a local mock with illustrative fixture names. They are not native, device or screen-reader evidence.
