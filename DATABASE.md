# Database
UUID PKs, UTC timestamps, foreign keys, RLS.

Core tables:
profiles: auth user id, display_name, preferred_mode, default_transport, points_balance, timestamps. Never expose email publicly.
locations: canonical Open Stall records: name/address/lat/lng, status (candidate|pending|unverified|verified|closed), restroom_evidence, restroom_verified/last_verified_at, nullable amenity/access/fee booleans, opening_hours, access_location, rating aggregates, manually_edited_at, possible_duplicate_of. Source/provenance lives in location_sources (many per location: source, reference, license, attribution, tags, hash, freshness). import_runs tracks importer runs. See IMPORT.md.
reviews: location/user/rating 1–5/mode/timestamps.
review_observations: structured factual observations.
submissions: user/type/target/proposed_data jsonb/status/moderator/reviewed timestamps. Pending data never canonical/public.
reports: location/user/controlled issue_type/optional comment/status/timestamps.
favorites: unique user+location.
checkins: user/location/time with anti-abuse.
point_ledger: append-only user/event/points/source/time.
achievements + user achievements.
referrals: inviter/invitee/status/reward eligibility/anti-abuse.
subscriptions: app entitlement state; billing provider remains source of truth.
moderation_log: material admin actions.

Enable PostGIS if appropriate and geospatial index.
Flag duplicate candidates by normalized address or roughly 50m proximity for admin review; do not auto-merge on distance alone.

Rewards P2 (local only, `supabase/rewards-wip/R005`-`R006`, disposable PostgreSQL 16; not a migration): new tables `rewards.reward_decisions` (immutable reward audit; `admin_id` is a plain id like `moderation_decisions.reviewer_id`), `reward_holds` (one active per account; only a single valid clearance update; delete only 90 days after clearance), `visit_clearances` (immutable outcome of a held visit), `reward_deleted_aggregate_month` (anonymous, month-keyed, grow-only). Changes to P1 tables (R005): `visits.user_id/idempotency_key/distance_bucket` and `reward_ledger.user_id` become nullable (identity severing only, with a check that they sever together), the ledger gains `reward_decision_id` and a new entry-shape check (reversal = negative, cites a final decision), and the P1 foreign key from `reward_ledger.moderation_decision_id` to `public.moderation_decisions` is dropped (it changed the error code of TRUNCATE on that existing table; the column is now always NULL). Replaced functions: `ledger_insert_guard` (validated reversals and cleared-hold awards), `check_visit_ledger_consistency` (clearance-aware), `record_visit_at` (an active hold records the visit as held), `guard_counter_monotonic`, and `public.delete_my_account` (existing body plus one `rewards.purge_my_reward_data()` call). Foreign keys to `auth.users` stay `on delete restrict`: promotion to a migration is still blocked until separately approved, and account deletion is only possible through the purge path.

Rewards P3 (local only, `supabase/rewards-wip/R007`-`R009`, disposable PostgreSQL 16; not a migration; rewards stay disabled and NO catalog row is seeded): new tables `rewards.achievement_definitions` (immutable versioned definitions; a change is a new version row, inserted only by the migration owner/tests), `achievement_chains` (opaque `chain_id`, account-scoped `(user_id, key, period)`, `user_id` NULL when severed), `achievement_events` (append-only award/revoke log, no user id; revoke events cite the lifetime reversal ledger entry and its P2 `reward_decisions` row) and `achievement_eval_queue` (repair queue, scope unioned, capped at 500 with an overflow flag). Engine in `R008` (`ach_*` helpers, one shared version selector, `evaluate_achievements`, `ach_run` hook wrapper, `ach_process_queue`), public `get_my_progress(cursor, limit)` (own progress only, `auth.uid()`, paged) and admin `repair_achievements(limit)`; `R009` extends the single purge function (queue deleted, chains without a revoke deleted with their events, chains with a revoke severed). Metrics read only standing (non-reversed) lifetime awards. Windows use the stored location-local date; the version is fixed by the window start (windowed) or by the recorded award (awarded lifetime chains). Chains are serialized by per-chain advisory locks, not `FOR UPDATE`, so the writer holds no UPDATE on chains. **Bounded work (after Work's review of 6537a09):** one engine call reads at most 5,000 standing awards in total (a single pass per distinct window, cached, so fifty lifetime definitions cost one scan), evaluates at most 50 chains, and returns what does not fit as `remaining` (resumed next call); a chain whose OWN window holds more than the whole budget is DEFERRED in `achievement_eval_queue.deferred` (never evaluated partially, reported `unavailable`, never retried in a loop). A supporting partial index `reward_ledger_standing_day_idx` makes a window an index range and distinct months loose index probes. A logical key keeps ONE window rule for ever (a different window type needs a separate key; refused at insertion). A new overflow truncation rewinds an in-progress re-scan cursor.
