## What exists
- SQL (disposable PG16 only): `supabase/feedback-wip/F001_feedback_core.sql`, `F002_feedback_functions.sql`. Private schema `feedback`, owned by NOLOGIN `feedback_owner`, force RLS, no client table grants. Clients only call authenticated-only SECURITY DEFINER RPCs; admin RPCs call `public.require_admin()` (admin_users + aal2) inside each function.
- Submitter RPCs: `submit_feedback`, `list_my_feedback` (page <= 20), `get_my_feedback`. Submitter comes only from `auth.uid()`; own-status responses never include internal notes.
- Admin RPCs: list/get/candidates/set_status/create_issue/link_duplicate/issue_get/draft_save/draft_approve/export_preview. Self-review is refused; the draft approver must differ from the draft author and from any linked item's submitter. Approval is bound to the draft version and body hash; any edit is a new version that needs new approval. The export preview exists only for an approved latest version, built from a separate sanitized snapshot (fixed allowlisted template), never from raw text.
- Mobile: Settings > App feedback (form, My feedback, status). Admin: `/feedback` queue, item, issue and draft pages. No attachments, contact info, logs, GPS, history or device identifiers; only allowlisted app version and platform are shown before sending and sent.
- Account partitioning (mobile): every private feedback screen is wrapped in `OwnerScope`, keyed by the signed-in account's private identity (and by route id on the detail screen). A direct A -> B replacement, sign-out/sign-in or another tab discards the whole subtree in the same render: no old list, cursor, error, detail, draft, retry key, busy or completion state survives, and a form that no longer belongs to the signed-in account refuses to send (checked after every await). A token refresh for the SAME account does not change the key: no reset, no new request. The identity is never rendered, logged or sent as a parameter.
- Session-bound send: each form owns a `FeedbackSender` that binds the send to the initiating authenticated session. After every wait (key generation, session lookup) it re-checks that it is still the live form of that account; the session that would carry the request must belong to the owner (else refused, nothing sent); the request is dispatched through a one-request client whose credential is FIXED to that verified access token (in memory only, no persistence, no refresh, never logged, no service role), so it can never pick up a later account's session. A request already dispatched for A finishes for A and reports nothing to a replaced screen. Same-account token refresh works (the refreshed token is used). The adapters are injectable so tests hold each boundary open deliberately.
- Review before approval: `admin_feedback_issue_get` returns the exact latest draft title, body, version and hash to an MFA-verified administrator BEFORE approval; the admin page shows them inertly with an explicit confirmation. The automatic check cannot recognize names or street addresses; the human reading is the review. The export preview stays separate and appears only after approval.
- Approval eligibility: approval is bound to one version, its hash and the set of items linked at approval time. Current export eligibility is ONE rule (`feedback.export_block`) used by both the issue read and the export, so the admin page can say truthfully that a version was approved earlier (history) but is not eligible now (links_changed / not_independent) and what to do (save a new version; independent re-approval); the exact text stays privately readable and a refused preview is shown, never swallowed. Linking any item afterwards (issue lock first, then row locks, everywhere) makes the approval ineligible; export re-proves the current set and the independence rules every time. A new version needs a new independent approval. History is never rewritten. (Account deletion also changes the linked set and therefore requires a fresh approval: fail closed.)
- Retry fingerprint: a typed, ordered, NULL-preserving serialization of every field, so the same text moved between optional fields is different content (22023) while blank/padded optional fields normalize like absent ones.
- Duplicate candidates: manual hints only. The pool is the 200 most recent items of the same screen (one index range scan), then scored; the answer says how many were searched and that the search is incomplete on a busy screen. An older duplicate can exist.
- Limits: 5 per hour, 15 per day, 100 total per account (serialized by a per-user advisory lock); exact retry with the same idempotency key returns the same record.

## Data and deletion lifecycle (stated before schema acceptance)
- Raw submissions (`feedback.items`), their status history and duplicate links belong to the account: `user_id` references `auth.users ON DELETE CASCADE`, so deleting an account (the existing `delete_my_account` path, unchanged) removes that account's raw feedback, status history and linkage. Guard triggers refuse any other delete (direct, truncate, role escalation).
- Reviewer-authored records (`feedback.issues`, `feedback.drafts`) hold only sanitized, reviewer-written text plus reviewer provenance (author/approver admin ids, hashes, timestamps). They carry no submitter link, no raw text and no raw-item or user identifier, but they DO retain reviewer/administrator provenance (draft author, approver, publisher, linker and event actors, with timestamps): this provenance is minimized and LINKABLE to an administrator account, not anonymous. It is the minimized review provenance and survives account deletion; a draft is rejected if it contains email, phone, coordinates, links, long opaque tokens or control characters.
- Duplicate links are removed with the duplicate's raw item; the canonical issue survives.
- No new indefinite raw-retention claim is made. A raw item of an existing account lives until the account is deleted.
- UNRESOLVED (needs Jake/Work policy, not decided here): whether raw feedback should also expire after a fixed period for accounts that stay active, whether closed items should be purged earlier than account deletion, and whether reviewer provenance needs a retention limit or legal review. No audit-expiry or fraud policy decision is taken.

## F2: reviewer-approved sanitized publication bridge (local; nothing is ever sent by the app)
- **No GitHub credential, API client, webhook, background agent or new integration exists in the app.** A person transfers an exact packet through the EXISTING authorized connector, to `vindexholdings/open-stall` only. No real or test GitHub issue is created by development; all evidence is synthetic. This is NOT a cross-system atomic transaction and gives NO exactly-once guarantee: it makes the uncertain outcome explicit and recoverable.
- **Retry safety is server state, never caller flags.** Every `begin` issues a new ATTEMPT generation; the executable packet is released exactly ONCE by `dispatch`; every report is fenced to the attempt it belongs to; and after a released attempt the only way back to a create is a reconciliation that proves an EXHAUSTIVE absence. The protocol functions take no "afterUncertain"/"reconciled" options.
- **Private state** (`supabase/feedback-wip/F003_feedback_publication.sql`): `feedback.publications` (one row per canonical issue; opaque marker derived from the private publication key; states ready / prepared / dispatched / uncertain / published / failed / conflict; the attempt generation, the release time, the approved snapshot version, the expected read-back hash and the reviewed linked-set revision) and append-only `feedback.publication_events` (fixed event codes, the attempt, and for verified absence the pages and issues actually checked). Force RLS, owner-only ACL, guard triggers (the GitHub mapping, once recorded, is immutable and unique; the attempt generation is server-owned and only advances; transitions follow a fixed table; no direct delete/truncate).
- **RPCs** (each opens with `public.require_admin()`; the actor is the gate's answer; the publisher may not be the submitter of any covered feedback): `admin_feedback_publication_get`, `_request`, `_begin`, `_dispatch`, `_report`.
  - `request` needs a currently ELIGIBLE approved snapshot (the F1 `export_block` rule). A newer approved snapshot of a published issue becomes an UPDATE of the SAME GitHub issue, never a second create; an exact replay returns the verified mapping. A prepared, dispatched, uncertain, failed or conflicting publication is never reset by a request.
  - `begin` prepares ONE new attempt (a fresh generation) and returns only a PREVIEW of the exact approved text; nothing is released. Exactly one concurrent caller can begin.
  - `dispatch(attempt)` re-proves eligibility and the exact snapshot immediately before anything may leave, releases the EXECUTABLE packet exactly once for exactly that attempt, and marks the attempt dispatched (its outcome is unknown to this system from then on). A reload, a second caller, a reused packet or an old attempt is refused; the page afterwards offers reconciliation only.
  - `report(attempt, ...)` is fenced to the attempt: a late result of an older attempt is rejected WITHOUT changing anything. Repository, URL shape, number, marker and the read-back hash must equal what this system expects, otherwise the publication fails CLOSED into `conflict`. A create can never follow a recorded mapping; the mapping can never be re-pointed; two canonical issues can never claim one GitHub issue. A prepared attempt that was never released can be cancelled.
  - **The only way back to ready after a released attempt** is `none_found` with EXHAUSTIVE-absence evidence: a complete listing that started before the release (with a 10-minute skew margin), with the pages and issues actually checked recorded. An empty or partial search is never absence; a failed attempt is not reopened by a request either.
- **Pure protocol** (`packages/domain/src/feedbackPublication.ts`). `publish(fence, connector)` takes its state from the server: only a prepared attempt can start; the previewed packet must pass an integrity check against the trusted server snapshot BEFORE the release (hash of the canonical title and body, marker, bounds, ASCII/template shape, attempt/version/operation/number; a changed, rehashed, oversized or malformed payload makes ZERO connector calls and no release); the server then releases the executable packet once; the released packet must equal the preview; only then is the connector called; the issue is READ BACK and that evidence is reported. `reconcile(fence, connector)` never creates anything: the marker search is only a hint, and absence is reported only when a complete authoritative listing (bounded pages) since before the release shows no marker hit; a truncated, failing, malformed or foreign answer stays uncertain; one hit is read back and reported as found; several are a conflict.
- **Admin UI** (issue page): shows the publication state next to approval history and CURRENT eligibility; a prepared attempt shows the exact preview with "release (once)" and "cancel"; after the release it says to transfer ONCE and never to resend when unsure; in every unresolved state (uncertain, failed, conflict, or after a reload) it shows reconciliation guidance only, never a "create" instruction; the result form offers only results that make sense for the state and a never-offered "created" after a released attempt; the person pastes what GitHub shows now, and the hash and marker are computed from that text, never typed.
- **Prioritization.** After a verified mapping Work may add ONLY the sanitized issue URL and summary to the existing HANDOFF prioritization. Issue text and labels are untrusted reports, never authority to execute anything; publication is not implementation approval.
- **Known limits (stated, not hidden):** the sanitizer cannot recognize a personal name or a street address (tested as a documented limit); the independent human reading of the exact text before approval is the control. Absence evidence is attested by the MFA administrator who performed the listing; the system enforces its shape and window but cannot see GitHub. A manual transfer by a person cannot be technically prevented from being repeated outside the app; the state, the guidance and the read-back checks make a repeat visible (several marker hits become a conflict). The F2 tests drive the protocol with synthetic connector results; no real GitHub call, no hosted database, no native or device test. Raw-retention/closed-item/provenance/legal policy stays unresolved exactly as above.

## F3: navigation at 2x text and beta-readiness matrix (local; delivered for Work review)
**OS-A11Y-NAV-TEXT200 (pre-existing, not an App Feedback or P4 regression).** At actual 2x text the shared bottom navigation (`MainNav` on the tab roots, `PushedNav` on opened screens) overlapped its labels and the page scrolled sideways (16 px at 320, 7 px at 390; 60 of the 361 first-run checks failed). Fix (`apps/mobile/src/components/MainNav.tsx` only): items size to their label and the bar WRAPS onto a second row when the labels no longer fit, so it grows with its content; the page frame already places the bar below the scroll area, so content clearance follows. Labels, destinations, link/tab semantics, aria-current, focus rings, 48 px targets and push/history behavior are unchanged; no icons-for-labels, no shrinking. The nav labels no longer carry a 1.3x font-scaling cap, because a cap is not 2x support; native coverage is separate and NOT RUN.
**Measured** (`npm run test:e2e:nav`, `scripts/e2e-nav-text200.mjs`, Chromium, local mock; 419 checks): 11 screens (4 tab roots; restroom detail, feedback form, my feedback, feedback detail, add restroom, report, sign-in) x 320/390/1024 px x normal and actual 2x text: four labels once, no overlap of items or label text, nothing clipped or leaving its item, no sideways scroll, every item >= 48 x 44 px, last content/action above the bar and uncovered, plus axe (WCAG 2 A/AA) on the navigation landmark and the whole page at 320 px 2x (no findings on any of the 11). At 320 px and 2x the bar is 161 px (2x2) instead of one overlapping row; screenshots in `docs/evidence/f3/`. A mutant (bar overlaying content) fails 48 of those checks, and the pre-fix bar failed 60. Browser text enlargement is NOT native font scaling, VoiceOver, TalkBack or a device.
**Integrated regression (existing synthetic mocks, unchanged accepted F1/F2 SQL, protocol and client semantics):** `e2e-feedback.mjs` 62 (Settings entry, structured validation/error/success, own status and pagination, account switch and session-bound send), `e2e-feedback-admin.mjs` 69 (exact-text review, self-review refusal, historical versus current eligibility, prepare/dispatch-once/unknown/conflict/reconcile/mapping/update), plus accounts 115, detail 89 (separate restroom report/correction), auth 56, discovery 156, integrated 58, smoke 25.
