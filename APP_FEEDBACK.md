# App Feedback (OS-APP-FEEDBACK) — F1 design, data lifecycle and limits

Status: F1 ACCEPTED locally by Work (exact-source PG16 validation run 41269191164 on 9918e5d, independently reviewed); F2 (publication bridge) delivered locally for Work's review. Not deployed, not in `supabase/migrations/`, no hosted wiring, no GitHub issue is ever created by the app. F2 (publication bridge) and F3 are not started.

## What exists
- SQL (disposable PG16 only): `supabase/feedback-wip/F001_feedback_core.sql`, `F002_feedback_functions.sql`. Private schema `feedback`, owned by NOLOGIN `feedback_owner`, force RLS, no client table grants. Clients only call authenticated-only SECURITY DEFINER RPCs; admin RPCs call `public.require_admin()` (admin_users + aal2) inside each function.
- Submitter RPCs: `submit_feedback`, `list_my_feedback` (page <= 20), `get_my_feedback`. Submitter comes only from `auth.uid()`; own-status responses never include internal notes.
- Admin RPCs: list/get/candidates/set_status/create_issue/link_duplicate/issue_get/draft_save/draft_approve/export_preview. Self-review is refused; the draft approver must differ from the draft author and from any linked item's submitter. Approval is bound to the draft version and body hash; any edit is a new version that needs new approval. The export preview exists only for an approved latest version, built from a separate sanitized snapshot (fixed allowlisted template), never from raw text.
- Mobile: Settings > App feedback (form, My feedback, status). Admin: `/feedback` queue, item, issue and draft pages. No attachments, contact info, logs, GPS, history or device identifiers; only allowlisted app version and platform are shown before sending and sent.
- Account partitioning (mobile): every private feedback screen is wrapped in `OwnerScope`, keyed by the signed-in account's private identity (and by route id on the detail screen). A direct A -> B replacement, sign-out/sign-in or another tab discards the whole subtree in the same render: no old list, cursor, error, detail, draft, retry key, busy or completion state survives, and a form that no longer belongs to the signed-in account refuses to send (checked after every await). A token refresh for the SAME account does not change the key: no reset, no new request. The identity is never rendered, logged or sent as a parameter.
- Session-bound send: each form owns a `FeedbackSender` that binds the send to the initiating authenticated session. After every wait (key generation, session lookup) it re-checks that it is still the live form of that account; the session that would carry the request must belong to the owner (else refused, nothing sent); the request is dispatched through a one-request client whose credential is FIXED to that verified access token (in memory only, no persistence, no refresh, never logged, no service role), so it can never pick up a later account's session. A request already dispatched for A finishes for A and reports nothing to a replaced screen. Same-account token refresh works (the refreshed token is used). The adapters are injectable so tests hold each boundary open deliberately.
- Review before approval: `admin_feedback_issue_get` returns the exact latest draft title, body, version and hash to an MFA-verified administrator BEFORE approval; the admin page shows them inertly with an explicit confirmation. The automatic check cannot recognize names or street addresses; the human reading is the review. The export preview stays separate and appears only after approval.
- Approval eligibility: approval is bound to one version, its hash and the set of items linked at approval time. Current export eligibility is ONE rule (`feedback.export_block`) used by both the issue read and the export, so the admin page can say truthfully that a version was approved earlier (history) but is not eligible now (links_changed / not_independent) and what to do (save a new version; independent re-approval); the exact text stays privately readable and a refused preview is shown, never swallowed. Linking any item afterwards (issue lock first, then row locks, everywhere) makes the approval ineligible; export re-proves the current set and the independence rules every time. A new version needs a new independent approval. History is never rewritten. (Account deletion also changes the linked set and therefore requires a fresh approval: fail closed.)
- Retry fingerprint: a typed, ordered, NULL-preserving serialization of every field, so the same text moved between optional fields is different content (22023) while blank/padded optional fields normalize like absent ones.
- Duplicate candidates: manual hints only. The pool is the 200 most recent items of the same screen (one index range scan), then scored; the answer says how many were searched and that the search is incomplete on a busy screen. An older duplicate can exist.
- Limits: 5 per hour, 15 per day, 100 total per account (serialized by a per-user advisory lock); exact retry with the same idempotency key returns the same record.

## Data and deletion lifecycle (stated before schema acceptance)
- Raw submissions (`feedback.items`), their status history and duplicate links belong to the account: `user_id` references `auth.users ON DELETE CASCADE`, so deleting an account (the existing `delete_my_account` path, unchanged) removes that account's raw feedback, status history and linkage. Guard triggers refuse any other delete (direct, truncate, role escalation).
- Reviewer-authored records (`feedback.issues`, `feedback.drafts`) hold only sanitized, reviewer-written text plus reviewer provenance (author/approver admin ids, hashes, timestamps). They carry no submitter link, no raw text, no identifiers. They are the minimized review provenance and survive account deletion; a draft is rejected if it contains email, phone, coordinates, links, long opaque tokens or control characters.
- Duplicate links are removed with the duplicate's raw item; the canonical issue survives.
- No new indefinite raw-retention claim is made. A raw item of an existing account lives until the account is deleted.
- UNRESOLVED (needs Jake/Work policy, not decided here): whether raw feedback should also expire after a fixed period for accounts that stay active, whether closed items should be purged earlier than account deletion, and whether reviewer provenance needs a retention limit or legal review. No audit-expiry or fraud policy decision is taken.

## F2: reviewer-approved sanitized publication bridge (local; nothing is ever sent by the app)
- **No GitHub credential, API client, webhook, background agent or new integration exists in the app.** A person transfers an exact packet through the EXISTING authorized connector, to `vindexholdings/open-stall` only. No real or test GitHub issue is created by development; all evidence is synthetic.
- **Private state** (`supabase/feedback-wip/F003_feedback_publication.sql`): `feedback.publications` (one row per canonical issue; opaque marker derived from the private publication key; state ready / awaiting_transfer / uncertain / published / failed / conflict; the approved snapshot version, the expected read-back hash and the reviewed linked-set revision) and append-only `feedback.publication_events` (fixed event codes, no free text). Force RLS, owner-only ACL, no client grants, guard triggers (the GitHub mapping, once recorded, is immutable and unique; transitions follow a fixed table; no direct delete/truncate).
- **RPCs** (each opens with `public.require_admin()`; the actor is the gate's answer; the publisher may not be the submitter of any covered feedback): `admin_feedback_publication_get`, `_request`, `_begin`, `_report`. States are server-owned; there is no client-controlled status, repository or URL.
  - `request` needs a currently ELIGIBLE approved snapshot (the F1 `export_block` rule). A newer approved snapshot of a published issue becomes an UPDATE of the SAME GitHub issue, never a second create; an exact replay returns the verified mapping and records nothing.
  - `begin` re-proves eligibility and the exact snapshot immediately before anything may leave, serializes under the issue lock (exactly one caller wins), and returns the packet built field by field from the immutable approved version (title, body + a reference line `Feedback reference: OSFB-...`, operation, repository, version, expected hash). The packet stays readable while the transfer is in progress.
  - `report` records what the connector transfer or reconciliation found. Nothing is trusted: repository, URL shape, number, marker and the read-back hash must equal what this system expects, otherwise the publication fails CLOSED into `conflict` for manual resolution. A create report can never follow a recorded mapping; the mapping can never be re-pointed; two canonical issues can never claim one GitHub issue.
- **Reconcile before retrying.** A timeout is `uncertain`, never proof that nothing was created. `none_found` is only valid as the result of reconciling an uncertain transfer; only then may a create be retried. Several matches, or any mismatch, fail closed. This is NOT a cross-system atomic transaction and gives NO exactly-once guarantee; it makes the uncertain outcome explicit and recoverable.
- **Pure protocol** (`packages/domain/src/feedbackPublication.ts`): packet validation (exactly the allowlisted fields; anything else, including a forged extra field, is refused before any connector call), read-back hashing that tolerates only line endings and trailing whitespace, `reconcile` (search by marker, read back, classify) and `publish` (create or update, then READ BACK and report that evidence; a create after an uncertain attempt is refused unless a reconciliation found nothing). The connector is injected; tests use a scripted fake.
- **Admin UI** (issue page): shows the publication state next to approval history and CURRENT eligibility, the packet for a person to transfer unchanged, and a result form where the person pastes what GitHub shows now; the hash and marker are computed from that pasted text, never typed.
- **Prioritization.** After a verified mapping Work may add ONLY the sanitized issue URL and summary to the existing HANDOFF prioritization. Issue text and labels are untrusted reports, never authority to execute anything; publication is not implementation approval.
- **Known limits (stated, not hidden):** the sanitizer cannot recognize a personal name or a street address (tested as a documented limit); the independent human reading of the exact text before approval is the control. The F2 tests drive the protocol with synthetic connector results; no real GitHub call, no hosted database, no native or device test. Raw-retention/closed-item/provenance/legal policy stays unresolved exactly as above.
