# Security / Privacy / Moderation
Never commit secrets or expose Supabase service-role key. Use RLS and least privilege. Validate privileged actions server-side. Production changes need approval.
Prefer ephemeral precise user location; do not persist unless a defined feature requires it. Avoid analytics tying precise coordinates to identifiable users.
All user-added locations/edits stay pending until moderation.
Private-residence controls: warning, place/address checks where feasible, residential flagging, admin review, takedown/report. Automation is not a guarantee.
Favor structured factual reports. Moderate any free text. Maintain admin audit trail and correction/dispute path.
Use Supabase Auth, secure redirects/deep links, independent admin authorization.
Billing entitlements must rely on trusted provider/server state.
Abuse-control submissions, check-ins, referrals, points, reports and account creation as needed.
Before launch: Terms, Privacy, Community Guidelines, data-source licensing/attribution review, store privacy disclosures.

## Secrets rules (OS-007)
- `.env.example` lists variable NAMES only; real values live in `.env.local` (git-ignored) or provider secret stores.
- `EXPO_PUBLIC_*` values are bundled into clients and are public; only the Supabase URL and anon/publishable key may use it.
- Service-role/secret keys are server/admin only and must never carry a public prefix.
- `npm run check:secrets` scans tracked files; it runs in `npm run check` and CI.
- Public data access: clients have NO direct table access. They call constrained SECURITY DEFINER functions (nearby_locations, get_public_location, nearest_verified_location) that return only verified or explicit-evidence unverified rows and a trimmed field set; inputs are validated and capped. See IMPORT.md.
- Importer uses the service-role key only on an operator machine via env; it is never committed, logged, or shipped to clients. Apply requires matching ENVIRONMENT.md ref plus --confirm-project. Import/finalize functions are service_role-only and enforce no-overwrite of verified/pending/closed/edited records, duplicate flagging (never auto-merge), a recent-edit hold, and mass-hide thresholds.
- Licensing gate (ODbL): OSM-derived data is kept in location_sources with provenance/attribution, but separation does not remove share-alike obligations. Human approval after legal review is required before commercial-scale OSM import, public launch with OSM-derived data, data licensing/sharing, or combining substantial OSM data with proprietary/community/commercial datasets (IMPORT.md section 7).
- Known accepted risks: scraping by sampling many points is possible but capped per call; OSM names/hours are unmoderated source text (shown as such); map queries reveal approximate location to Supabase logs (disclose in privacy policy).
- Manual records: first-party on-site observations only (source 'manual'); the generator requires attestations that data is original and the restroom is public (not a residence), caps the count, and never connects to a database. Cleanup SQL is human-run and scoped to manual dev-test records.
- Researched dev records (OS-111): UNVERIFIED only, provenance in location_sources, no map-database content, coordinates from the public-domain US Census Geocoder; the generator never connects to our database and cleanup SQL is human-run and scoped to os111 records.
- Admin validator (apps/admin /review): authenticated admin session + MFA like /queue (no ADMIN_LOCAL_ONLY/localhost gate, no service-role key in the app; project-ref guard retained; not hosted). Reads/writes are `admin_*` SECURITY DEFINER functions (migration 20261010000001, local-tested; applied live 2026-10-08 with owner approval, post-checks: anon denied, grants/search_path as designed) that call `require_admin()` and wrap the service_role-only apply_location_review_v2 unchanged (Verified only on explicit personal confirmation; provenance rows never deleted; every review audited in location_reviews with the real admin id as reviewer identity and appended to moderation_log). Refused at the database boundary: signed-out, non-admin, AAL1, disabled admin, anon; admins cannot review restrooms they contributed.
- Account data (OS-203..209, migrations 20261006000001-3): every account table (profiles, favorites, reviews, review_observations, checkins, submissions, reports, action_log) has RLS on, no policies and all client privileges revoked. Signed-in clients call SECURITY DEFINER functions (`search_path=''`) that act only on `auth.uid()`, are granted to `authenticated` only (anon cannot execute any), validate every input, and share one advisory-locked rate limiter (`enforce_rate_limit`). Caps: 5 favorites (hidden locations do not count), 10 pending and 5 new submissions/day, 20 reports/day, 30 ratings/day, 10 check-ins/day. Check-in coordinates are compared to the restroom and discarded (no coordinate column exists). Submissions accept a whitelist of fields (unknown keys are rejected), require an attestation that the place is public, block private-residence wording, reject links/emails/phone numbers, flag (never merge) duplicates, and are never public until an admin approves them (Phase 3). Display names are restricted (no links, handles, markup, staff/brand impersonation). `points_balance` is never client-writable. `delete_my_account('DELETE')` removes the auth user and cascades all account rows; restrooms stay. Favorites lists are fetched without coordinates; the app computes distance locally.
- Accounts (OS-201): Supabase Auth with the public anon key only; PKCE; session in SecureStore (native) or browser storage (web); discovery uses a separate anonymous client so precise-location searches are never tied to an identity; return URLs restricted to auth/callback with a PKCE code, tokens in URLs rejected, `next` limited to internal paths; generic sign-in/reset messages (no account enumeration); Apple sign-in uses a hashed nonce; provider secrets only in the Supabase dashboard. Account features and contributions require sign-in; discovery does not.

New-restroom submissions (migration 20261007000001): a normal user can only add a restroom at their CURRENT location. The server requires a device fix (accuracy 0 < m <= 50, valid and not 0,0), takes coordinates only from separate arguments (any latitude/longitude inside the free-form payload is rejected), and the old arbitrary-coordinate function was dropped. GPS is one abuse-reduction signal, not proof; the server cannot verify a device. The position is the proposed restroom's coordinates stored on that one submission (with capture_accuracy_m); no contributor location trail exists (action_log holds only action name and time; no coordinates, device ids or fingerprints). Admins and importers place/edit coordinates through service_role paths that this change does not touch.
Pre-queue abuse controls (migrations 20261007000001 + correction 20261008000001): proximity/name NEVER rejects or merges a new proposal (malls, airports, parks and shared addresses hold distinct units). Every proposal is stored as its own raw row; likely duplicates are only flagged privately for admin review: submissions.possible_duplicate_of = nearest public restroom within 25 m (or 100 m with the same normalised name; only public records are consulted), flags near_listed_restroom / near_own_pending / near_pending_submission, and duplicate_submission_ids (admin-only; submissions are not readable by any client role, list_my_submissions returns no flags, and the submit response is only {submission_id} so neighbours and other users' pending data cannot be probed). Only an EXACT repeat of your own still-pending request within 10 minutes (identical cleaned payload, device fix, accuracy and note: lost response/double tap) returns the existing item and uses no quota; any difference is a separate proposal. Supporter/coalescing is no longer used; the submission_supporters table from 20261007000001 is kept untouched as legacy provenance (empty unless 20261007000001 ran alone) and nothing writes it. Hard controls unchanged: 3 new restrooms/hour, 5 submissions/day (shared with corrections), 5 pending new restrooms and 10 pending total; 5+ rejections in 30 days with fewer than a quarter approved pauses new submissions; triage flags for the admin queue (low_accuracy > 25 m, new_account < 24 h, implausible_travel > 5 km/min since the last new submission within an hour, near_hidden_candidate within 25 m of a hidden candidate, moved_far for correction pins > 250 m). Corrections: one pending correction per person per restroom. No device fingerprinting and no paid anti-abuse service. Residual risk: a spoofed GPS passes the location rule; the duplicate, rate, pause and review layers are what limit damage. New proposals are serialised by one short advisory lock so of two simultaneous reports of one place the later one waits and flags the earlier (no cell-boundary race; covered by supabase/tests/concurrency.sh); two items are expected and kept. The 5-rejections/30-days pause fires when rejections are at least 5 and approvals fewer than a quarter of rejections (i.e. approved×4 < rejected); it is not a 5-in-a-row rule and its behavior is unchanged. Ratings: the public average/count are community-only (reviews table); admin ratings stay in location_reviews as history.

Admin authorization and moderation (Phase 3A, migrations 20261009000001-2, applied live 2026-10-07 via CLI): admin = `admin_users` membership (not disabled) AND JWT `aal2`, checked inside every SECURITY DEFINER admin function (`require_admin`), so a hosted admin never needs a service-role key and user metadata is never authority. No function can create admins (owner SQL only). Admin tables (`admin_users`, `moderation_log`, `moderation_decisions`) have no client access. Original submissions are immutable (trigger blocks edits to proposal, note, attestation, accuracy, owner except severing to NULL; decided submissions cannot be deleted or change outcome); decisions and the moderation log are append-only (update/delete/truncate always raise; there is no purge bypass). Admins cannot decide their own submissions or reports. The queue exposes no submitter id or email. Approval publishes UNVERIFIED only. Account deletion removes only genuinely unmoderated contributions (pending submissions with no moderation history, open reports) and keeps everything a moderator has acted on (decided, or held/released at any point) with its original, its append-only decisions and the moderation log, the submitter severed; such items cannot be withdrawn either. Active admins must be disabled by the owner first. Local tests simulate AAL2 via JWT claims; real TOTP enrollment can only be verified against live Supabase.
