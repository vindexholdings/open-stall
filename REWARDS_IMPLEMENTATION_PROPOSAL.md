## 2. Precise source boundaries (P1)
- **New migrations live OUTSIDE `supabase/migrations/`**, in `supabase/rewards-wip/` (files `R001_...sql`, ...). The ordinary migration tooling (`supabase db push`, `supabase migration up`) discovers only `supabase/migrations/`, so the boundary directory prevents ORDINARY migration discovery. It does not prevent every possible manual execution: a person could still run a file with `psql` against any database. The protection against that is the harness's isolation and checks (section 3), the owner gate, and review, not the directory name. Moving a file into `migrations/` is a separate, explicitly approved step.
- New harness `scripts/test-db-rewards.sh` (a copy of the `scripts/test-db.sh` pattern: throwaway cluster in a `mktemp` directory on a unix socket, destroyed on exit) applies `supabase/tests/bootstrap.sql`, then `supabase/migrations/`, then `supabase/rewards-wip/`, then runs `supabase/tests/rewards/*.test.sql` and `supabase/tests/rewards/*.sh` (two-session). New npm script `test:db:rewards`. It is NOT added to `npm run check` or CI until P1 passes and Work agrees.
- New check script `scripts/check-rewards-boundary.mjs`: fails if any file in `supabase/migrations/` references a reward table or function, if `rewards-wip/` contains a name already in `migrations/`, or if any rewards file mentions a connection string, project ref or key. It is run by the harness and, once accepted, by `npm run check`.
- **Untouched in P1:** all existing migrations, `check_in` and its 12-hour/10-per-day behavior, `apps/mobile`, `apps/admin`, `packages/*`, CI workflows, `.env*`, docs other than state files and this proposal's follow-ups.
- Allowed new files only: `supabase/rewards-wip/*`, `supabase/tests/rewards/*`, `scripts/test-db-rewards.sh`, `scripts/check-rewards-boundary.mjs`, `docs/evidence/rewards/*`, plus edits to `package.json` (one script), `PROJECT_STATE.md`, `BACKLOG.md`, `TESTING.md`, `HANDOFF.md`.

## 3. Disposable-only environment safety and default-disabled behavior
- **Pinned, fully isolated harness (verified by behavior, not by text).** The harness requires PostgreSQL major version 16 exactly (the version installed in this environment) and aborts on any other. It starts the child `initdb`, `postgres` and `psql` processes with `env -i` plus an explicit minimal environment (`PATH`, `LANG`, and its own socket directory, port, user and database only), so NO inherited connection override can reach a child: `PGHOST`, `PGPORT`, `PGSERVICE`, `PGSERVICEFILE`, `PGPASSFILE`, `PGSSLMODE`, `PGOPTIONS`, `PGDATABASE`, `PGUSER`, `DATABASE_URL`, `SUPABASE_*` and the rest are all dropped. It never reads `.env*` and never accepts a hosted connection. **A self-test proves the behavior:** it runs the harness with poisoned variables (`PGHOST=example.invalid`, `PGSERVICE=prod`, `DATABASE_URL=postgres://invalid`) and asserts that every statement ran on the harness's own unix socket (`inet_server_addr()` is NULL, the server's `unix_socket_directories` equals the throwaway directory, and no TCP listen address is configured), and that an attempt to connect elsewhere fails. The textual scan of rewards files for connection strings and keys is only defense in depth.
- **One source of truth, explicitly split.** `reward_policy_versions` holds ONLY the immutable economic parameters (points per visit, lifetime first-daily points, rewarded visits per location-day, the per-user UTC-day spendable cap) with `effective_from` strictly in the future for any new row, so changes are prospective. `reward_settings` holds ONLY the operational switch and budget (`rewards_enabled`, `global_budget_utc_day`; NULL means unset) and is the single place either is read; the budget and the switch are NOT policy-version columns. Any change to settings appends a row to an append-only `reward_settings_history` with a server timestamp, and each visit records the settings row it used, so transitions are prospective and reproducible (a change affects visits accepted after it, never earlier ones). The migration inserts `rewards_enabled = false`, `global_budget_utc_day = NULL`. No client role and no P1 function can change settings. **Test fixtures cannot bypass production gates:** the only code that enables rewards or sets a budget lives in `supabase/tests/rewards/fixtures.sql`, which only the throwaway harness executes; `supabase/rewards-wip/` must contain no function or statement that enables rewards or sets a budget, and the boundary check fails if it does. Tests that need rewards enabled run the fixture inside the throwaway cluster, never as part of the migrations. A post-migration assertion on a fresh cluster proves: settings are disabled and unset, `record_visit` records a visit and issues nothing (both outcomes `rewards_disabled`), and the ledger and counters are empty.
- Legacy `check_in` is regression-tested unchanged (same 12-hour guard and 10/day limit) in the same run, so coexistence is proven rather than assumed. Anonymous discovery functions and their grants are compared before and after (golden catalog diff).

## 4. Roles and privileges (separating writer, client and purge)
| Role | Kind | Rule |
|---|---|---|
| `anon` | client/API | nothing: no table, schema or function privilege on any rewards object |
| `service_role` | client/API (bypasses RLS by Supabase design) | no privilege either: no table, schema or function privilege, so RLS bypass is moot |
| `authenticated` | client/API | no table privilege of any kind; `EXECUTE` ONLY on its permitted RPCs: `record_visit` (P1) and later `get_my_progress`, and the admin RPCs gated inside by the existing admin identity and MFA (P2/P3). Never on internal functions |
| `reward_writer_owner` | NOLOGIN, NOINHERIT, no BYPASSRLS | owns the SECURITY DEFINER writer functions; may INSERT/SELECT (and UPDATE only on counter tables); NO DELETE, NO TRUNCATE, and NO UPDATE on the ledger, visits, chains or events |
| `reward_purge_owner` (P2) | NOLOGIN, NOINHERIT, no BYPASSRLS | owns only the purge function; DELETE and column UPDATE exactly as in `VIP_REWARDS_PLAN.md` section 7 and `ACHIEVEMENTS_PLAN.md` section 6; NO INSERT |
| table owner / migration role | superuser-like | not used at runtime; guard triggers still refuse protected changes by `current_user` |
Every protected table has statement-level `BEFORE TRUNCATE` triggers that always raise, and row-level append-only triggers (invoker security, fixed `search_path`, `current_user`-based). Function entry matrix: public RPCs `record_visit` (P1), `get_my_progress` (P3) = `authenticated` only; admin RPCs `reverse_reward`, `clear_hold`, `repair_achievements` (P2/P3) = `authenticated` with the existing admin identity and MFA gate checked inside; internal `evaluate_visit`, `evaluate_achievements`, award blocks, queue helpers = NO client EXECUTE (non-exposed schema, revoked from `public`, `anon`, `authenticated`, `service_role`); purge = EXECUTE only to the owner of `delete_my_account`. **Tests are golden catalog queries, and the inventory is complete, not inferred from role names**: for every rewards object enumerate with `aclexplode`, `has_*_privilege` and the catalogs: table, column, sequence, function and SCHEMA privileges (`USAGE`/`CREATE`), OWNERSHIP (`pg_class.relowner`, `pg_proc.proowner`, `pg_namespace.nspowner`), DEFAULT privileges (`pg_default_acl`, including the Supabase-style grants to `anon`, `authenticated` and `service_role` that `bootstrap.sql` mirrors) and any `PUBLIC` grant, and compare to the expected set (any extra grant fails). The internal writer's power is DEMONSTRATED: every SECURITY DEFINER function shows a fixed `search_path` in `proconfig` and schema-qualified references; tables have RLS enabled and FORCED (`relrowsecurity`, `relforcerowsecurity`) with the explicit policy list asserted; and a session `SET ROLE reward_writer_owner` (and each other role) performs the allowed operations and is refused the forbidden ones. attempt each forbidden operation as each role and expect `42501` or a trigger refusal, including TRUNCATE; independent MFA adjudication and append-only moderated originals are asserted unchanged.

## 5. Bounds to prove, not assume (applies to P1-P3)
| Bound | Provisional value | Proof required |
|---|---|---|
| repair users per call | 20 (server maximum) | invalid `p_limit` (NULL, 0, negative, above 20) rejected with `22023` or clamped as documented; test both |
| chains per user per evaluation call | 50 | processing remainder retained in `dirty_scope` |
| ledger rows scanned per evaluation call and elapsed time | proposed 5,000 rows and 2 s (local `statement_timeout` as a guard, not as handled flow) | representative data: one user with about 3,000 lifetime rows over 36 months (many windows) and 2,000 users with 30 days each; record `EXPLAIN (ANALYZE, BUFFERS)` and timings; if limits are exceeded, adjust and document, never silently widen |
| public progress paging | page size at most 50 chains, cursor-based | a user with 500 chains pages without scanning all history per request; invalid page size rejected |
| `dirty_scope` size | capped (proposed 500 chains) with an overflow flag meaning a bounded full re-scan | merge test: scopes are UNIONED, never overwritten; overflow behaves as specified |
| lock starvation | skipped users keep their row; order by `last_attempt_at` nulls first then `first_failed_at` | with one user's lock held repeatedly, other users' rows are still processed and the held user is eventually processed once released |
Queue data is user-linked repair data: it is deleted by the purge (test: no queue row survives deletion), never retained.

## 6. Version rule and failure handling (carried constraints)
- Progress reads and evaluation both call one `ach_effective_version(chain)` function: an awarded chain uses the version recorded on its latest `award` event; a revoked or unawarded lifetime chain uses the latest version in effect; a windowed chain uses the version fixed by the window start. Required test: threshold change, then reversal (revoke under the old version), then re-earn under the new version (`ACHIEVEMENTS_PLAN.md` section 4).
- Recoverable SQLSTATE handling is a HYPOTHESIS: the harness verifies on real Postgres 16 that `55P03` under a local `lock_timeout` is caught inside the block, that `57014` (statement timeout and cancellation, including `pg_cancel_backend`) behaves as feared and therefore propagates, and that `42501`, class `23` (other than designed no-ops), `40001`, `40P01` and class `XX` always propagate and abort the whole transaction. A handler never uses `when others`. Production safety gates (`rewards_enabled`, unset budget) are checked BEFORE any award block and cannot be bypassed by a caught error.

## 11. P2 implementation record (Work release `b0a1d8b`; delivered for review)
P2 is the local lifecycle/security slice on disposable PostgreSQL 16 only: audited reversal, existing-MFA-admin hold/clear with original-day clearance awards, the narrow account-deletion purge with identity severing and month-keyed anonymous aggregates, reconciliation, and the approved 90-day expiry of cleared holds. Boundary kept: no UI/admin screens, no hosted database, no production rewards (still disabled, budget unset), no migration promotion, no dependency/cost/service, no P3/P4. Design decisions taken inside the release (each is a review point for Work): (1) the original award is serialized by the user and user/location/day advisory locks that every writer of those rows takes, not by `FOR UPDATE`, so the writer needs no UPDATE privilege on the ledger or visits; (2) "retained evidence" = ever held, decided, cleared or reversed visits with all their ledger rows (a held-then-cleared visit is therefore severed and kept, not aggregated); (3) hold clearance outcomes live in `visit_clearances` because visits are append-only; (4) `admin_id` carries no foreign key so a disabled administrator can delete their account; (5) `expire_cleared_holds()` exists but nothing schedules it (no new service); (6) the confirmed-fraud audit retention duration remains an unresolved owner policy and nothing implements it. Files and evidence: see `TESTING.md` and `docs/evidence/rewards/README.md`.
